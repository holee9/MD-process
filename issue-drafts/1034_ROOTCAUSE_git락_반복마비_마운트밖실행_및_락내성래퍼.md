## 증상 (반복·다회차)

`.git/*.lock` 이 남으면 이후 **모든 git 쓰기 명령이 즉시 실패**한다.

```
fatal: Unable to create '.../.git/index.lock': File exists.
```

이 때문에 사이클이 작업을 마치고도 커밋 단계에서 조용히 죽는 일이 여러 차례 반복됐다. `.git` 디렉터리에 과거 세션들이 손으로 치운 흔적(`HEAD.lock.bak*`, `*.lock.old*`, `*.lock.rm*` 등)이 **37건 누적**되어 있었던 것이 반복의 직접 증거다.

## 근본원인 (2026-09-18 실측 확정)

git의 락 프로토콜은 **자기가 만든 락을 스스로 지울 수 있다**는 것을 전제한다. 그런데 이 저장소가 놓인 마운트는 그 전제를 만족하지 않는다.

| 위치 | 삭제(unlink) | rename | 비고 |
|---|---|---|---|
| 마운트 안(`.../의료기기 제조 업무규칙 개발`) | **세션 권한 있을 때만** | 항상 가능 | 권한은 세션 종료 시 소멸 |
| 마운트 밖(VM 자체 공간) | **항상 가능** | 항상 가능 | 제약 없음 |

즉 **"git이 자기 락을 지울 수 없는 곳에서 git을 돌린 것"** 이 원인이다. 락 정리는 증상 대응일 뿐이고, 권한이 사라지는 다음 세션에서 반드시 재발한다.

## 대책 (3중)

### 1. 구조적 제거 — 마운트 밖 실행 (`scripts/run_cycle.sh`)
사이클을 마운트 밖 작업 클론(`~/.mdprocess-work`)에서 수행한다. 삭제 제약이 없으므로 **락 문제가 성립하지 않는다**. 최신화→빌드→frontmatter 검증→커밋→push→사후검증→마운트 폴더 동기화까지 완주하며, 마운트 폴더에 미커밋 변경이 있으면 덮어쓰지 않고 보존한다. 커밋 identity는 마운트 저장소 설정을 승계한다.

이는 README가 원래 정의한 설계(`/tmp/wk-* 신규 클론에서 작업 → push`)와도 일치한다 — 설계를 벗어나 마운트 폴더에서 직접 돌린 것이 문제의 시작이었다.

### 2. 인플레이스 보호 — 락 내성 래퍼 (`scripts/git_safe.sh`)
마운트 폴더에서 git을 써야 할 때 사용한다.
- 호출 전 **오래된** 락 정리, **방금 생성된 락(작업 중인 git)은 보존**(나이 기준 45초, 조정 가능)
- 삭제 실패 시 **rename 우회**(rename은 항상 가능)
- 락 오류 감지 시 정리 후 자동 재시도(기본 3회), 그래도 실패하면 명확히 보고(조용한 실패 금지)
- `--clean` / `--purge` 로 락·누적 잔재 청소

### 3. 감시 (`scripts/check_pipeline_health.py`)
- **락 잔존 건수** — 1건이라도 있으면 경보(그 상태에선 이미 모든 git 쓰기가 막혀 있음)
- **정리 잔재 누적** — 10건 초과 시 경보(같은 문제가 반복되고 있다는 신호)

## 검증 (실기)

| 항목 | 결과 |
|---|---|
| 오래된 락 심고 맨 `git add` | `fatal: ... File exists` — 마비 재현 |
| 동일 조건에서 `gs_git add` | 정상 스테이징, 락 잔존 0건 — **복구 확인** |
| 방금 생성한 락 | 보존됨 — 작업 중 git 보호 확인 |
| 삭제 권한 없는 상황(rename 강제) | 복구 성공 — 권한 비의존 확인 |
| 누적 잔재 37건 | 청소 완료 |
| `run_cycle.sh` end-to-end | 커밋·push·사후검증 통과, **락 미발생** |
| 락 감시 | 심은 락 1건 즉시 검출 및 조치 안내 |
